## Implementation and schema

[DATABASE](../../DATABASE.md) and [implementation differences](../../database/IMPLEMENTATION.md) describe Flyway V0001–V0015: the original JDBC-session baseline plus incremental domain, constraint, privilege and forward corrective migrations. [Accepted migration hashes](migrations-sha256.json) are checked in CI; never edit an applied migration. There are 100 domain tables, two framework session tables and Flyway history. The actual [catalog audit](schema-audit.json) records 103 tables, 881 columns, 1,450 constraints and 374 indexes; every referencing FK has a leading index. Counts include framework tables and auxiliary indexes, not 103 new domain entities.

Stable identities/routes, ordered memberships, immutable sealed revisions and publication manifests, typed content/provenance/rules, ownership, exact assessment versions, draft/submitted answers, exposure, remediation, fixed enrollment requirements, optimistic versions, job leases and minimal erasure records are enforced through typed columns, keys, checks and transactional triggers. PostgreSQL rather than H2 is the only tested persistence engine. Small JPA/JDBC repositories cover concrete tested access paths, without generic CRUD endpoints or eager entity graphs. Passwords use versioned Argon2id hashes with random salts; no shared administrator or application account is seeded.

The runtime, importer and privacy groups have separate privileges. Local credentials are generated, ignored and distinct from the migration owner. Production startup rejects schema-owning/elevated runtime roles and requires migrations to run separately. Import parsing, authentication adapters, feature orchestration and external privacy/recovery workflows remain their later stage assignments.

## Query experiment and limits

The runnable test-classpath `P08QueryPlan` creates and removes its own PostgreSQL container. All constraints/triggers remain enabled. It loads 5,000 synthetic accounts, 255,000 enrollment requirements, 250,000 progress records, 50,000 notes, 100,000 bookmarks, 200,000 attempts and 1,000,000 answers. Catalog coverage includes 2,851 read-only canonical identities plus complete synthetic test bodies; **canonical bodies/relationships are not imported**. Ten-version history, a heavy attempt owner, a zero-progress owner, retirement/withdrawal and tag fan-out are exercised separately. The final V0015 run took 183.80 seconds to load the baseline. Warm execution times were 0.105 ms for route lookup, 0.892 ms for search, 0.074 ms for owned notes, 0.126 ms for the frozen denominator and 0.321 ms for answers. History/skew cases ranged from 0.022 to 0.256 ms. Exact sizes and EXPLAIN ANALYZE/BUFFERS plans are in the report.

These are warm single-database plans after load/ANALYZE, not cold-cache results, concurrent HTTP percentiles, all P04 discovery queries, or a capacity/SLA claim. P09 must prove real canonical relationship import and preservation; P10 must measure its implemented query combinations; P20 must measure realistic concurrent end-to-end load. The benchmark never writes synthetic fixtures to the local application or packages them in the production JAR.

## Failures and repairs

Initial DDL construction exposed forward-reference ordering and identifier/parser mistakes; table creation and FK/check allocation were separated before acceptance. Real integration tests then exposed overly broad erasure immutability, missing privacy-role token revocation permission, optimistic native-write gaps, session challenge deletion behavior and seal/hash/assessment consistency omissions. Forward migrations V0009–V0013 repair these while retaining the accepted baseline.

The final V0014 test run caught a shared trigger inspecting fields from the wrong table (`record new has no field kind/reinstated_at`). V0015 isolates the table-specific branches. The invalid-reference helper requires an integrity/permission SQLSTATE, so SQL grammar failures cannot count as passing negative tests. All affected tests were rerun successfully. No applied migration, checksum or assertion was edited to hide a failure. Final documentation validation also caught an extra ERD view without the two P05 dictionary rows and a singular/plural evidence-link mismatch; the extensions were merged into the existing three views, their dictionary rows documented and the link corrected. Recursive checks then passed. Trivy emits unsupported optional SBOM hash-algorithm warnings but completes its package vulnerability scan; its exit status and report, not absence of warnings, determine the gate.

P07's original missing-runtime/Docker/port failures remain in its review. Docker was healthy for the final P08 runs; no H2 replacement or skipped PostgreSQL gate was used. No external message, paid service, remote commit/push or deployment occurred. The local development stack remains available; documented shutdown preserves its volume. P09 is the next eligible prompt only when requested.
