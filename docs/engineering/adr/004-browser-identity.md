# ADR-004 — Same-origin sessions and privileged second factor

Accepted for design, 23 September 2026. [Security](../SECURITY.md) is normative alongside this decision.

## Decision and alternatives

Use Spring Security username/password authentication and **Spring Session JDBC** in PostgreSQL. The browser holds an opaque session ID; it does not hold a JWT, refresh token or user role claim. [JDBC session support](https://docs.spring.io/spring-session/reference/configuration/jdbc.html) supplies indexed sessions and expiration cleanup. All authentication, roles, ownership and recent-auth checks live in Spring, including SSR reads. No NextAuth/Auth.js identity database and no second frontend session.

JWTs in localStorage increase script-theft exposure and complicate immediate logout/revocation. Cookie-carried JWTs still require CSRF controls and add revocation machinery with no R1 mobile/third-party API requirement. A managed OIDC provider can be useful later but adds cost, processor/region and account-linking dependencies while P02 requires email/password/recovery and U01/U02/U05 are open. Neither is selected. Spring Session in Redis is valid at larger load; the initial 5,000 accounts/50 concurrent sessions do not justify a second store.

## Cookie, origin and SSR contract

Production uses one origin, illustrated only as `https://learn.example.invalid`: `/api/**` reaches Spring; other paths reach Next through the ingress proxy. Use `__Host-OTRSESSION`, Secure, HttpOnly, SameSite=Lax, Path=/, **no Domain**. The root path permits SSR to receive the cookie; HttpOnly prevents browser JavaScript reading it. Cookie expiry never exceeds the server's absolute limit. Spring rotates the ID after authentication and privilege elevation. Caddy preserves separate Set-Cookie headers. No wildcard credentialed CORS: disable cross-origin API access in R1; development also uses one origin. A second frontend domain would require a reviewed ADR change, not `Allow-Origin: *`.

Choose session-backed CSRF tokens via Spring's HttpSessionCsrfTokenRepository. A same-origin, uncached `/api/auth/csrf` read exposes the framework-generated masked token to the page; send it in `X-CSRF-TOKEN` for every unsafe operation, including login, logout, registration and recovery. Keep it in memory only. Public catalog reads create no session. Pre-auth CSRF sessions expire after 15 idle minutes and their creation is rate-limited; successful login applies the authenticated lifecycle. Fetch a fresh token after authentication/logout or session expiration; never retry an unsafe write automatically after token failure. This uses [Spring's documented token endpoint/session and BREACH handling](https://docs.spring.io/spring-security/reference/servlet/exploits/csrf.html), not an invented double-submit implementation. A future choice of CookieCsrfTokenRepository must use its SPA integration and be separately tested.

Additionally validate Origin on unsafe browser requests against the configured origin; if absent, require a same-origin Referer or reject. Reject cross-site Fetch Metadata unsafe requests. GET/HEAD have no business mutations; email-token GET only displays a confirmation form. Fixed server configuration creates email links and WebAuthn RP/origin values; never trust a supplied Host/Forwarded header. Caddy normalizes forwarded host/protocol; Spring does not blindly trust incoming forwarding headers. Next SSR forwards only the named session cookie to a fixed Spring address, with no user-controlled URL. It must not pass request headers to arbitrary remote sources.

## Passwords, lifecycle and storage

Meet REQ-16's 15–128 Unicode-codepoint acceptance, password-manager/paste support and compromised/common-password blocking. Use Spring's versioned DelegatingPasswordEncoder with **Argon2id** as the encode choice, supported by [Spring password encoders](https://docs.spring.io/spring-security/reference/features/authentication/password-storage.html); supply its required cryptography dependency from the managed dependency set. Start with 19 MiB memory, two iterations and parallelism one, then benchmark and strengthen within the 1-second login target. Record the actual parameters; do not truncate UTF-8 passwords to bcrypt's byte limit. Bound concurrent password hashing and request size to limit CPU/memory abuse. No password hints, plaintext, reversible password storage or homegrown hashing. Use a local maintained compromised-password blocklist; never send full passwords to an external service.

Verified learners: idle 24 hours, absolute seven days. Privileged accounts: idle 15 minutes, absolute eight hours; warn and offer deliberate reauthentication. Recent authentication within five minutes is mandatory for sensitive account/privileged actions. A session retains original authentication times; ordinary access cannot extend absolute or recent-auth limits. No persistent remember-me token. Per-account generation/version checked against authoritative account state prevents deleted, suspended, password-reset or role-revoked sessions from remaining effective. Do not trust an old role serialized in a session. Index sessions by principal for current/all-session logout; invalidate on password reset/change and sensitive identity changes. Enforce revocation again inside sensitive write transactions so an in-flight edit cannot commit after account revocation.

Verification tokens: single-use, 24 hours. Recovery tokens: single-use, 30 minutes; no automatic login after reset. Store only cryptographic token digests; consume transactionally. Token secrets are CSPRNG-generated by established Java libraries, not derived from account IDs. Revoke old outstanding tokens when replaced; purge expired/revoked secrets within 24 hours. Use generic recovery responses and bounded timing; 10 failed logins/account/15 minutes triggers a 15-minute throttle, plus source and global limits. Reset/resend ceilings are five/hour/address and 20/hour/source including unknown addresses. Email change requires recent authentication, verification of the new address and notification of the old one; preserve old identity until success. Outbox retries must expire with the underlying token and must not write tokens into logs. Email HTML is escaped; no content from notes enters mail.

The mail outbox stores a delivery intent and account/request reference, not a raw token. Its worker generates the secret in memory immediately before delivery and commits only its digest/expiry; a retry after an uncertain send issues a replacement and invalidates the previous token. The UI tells users to use the latest message. Thus durable retries do not require plaintext bearer secrets in a job table. Exclude ephemeral sessions, challenges and recovery/verification tokens from logical recovery exports; restore starts with every session/token invalidated. Provider message retention is separately reviewed under U05 and is not confused with application token validity.

## Privileged MFA and recovery

Editors, reviewers/publishers and administrators require **password plus WebAuthn**. Use the Boot-managed `spring-security-webauthn` module and the framework's `FACTOR_PASSWORD` / `FACTOR_WEBAUTHN` authorization support; [passkey registration/assertion](https://docs.spring.io/spring-security/reference/servlet/authentication/passkeys.html) and [MFA with factor recency](https://docs.spring.io/spring-security/reference/servlet/authentication/mfa.html) are documented for the selected line. Require user verification, exact RP/origin match, short single-use challenge, and account-bound challenge state. Persist framework credential repositories in PostgreSQL; do not copy documentation's in-memory demo repositories into production.

The requirement is **role-based and unconditional**: an editor with no enrolled key is denied privileged access. Do not use the example's “MFA only if already registered” condition, which could allow a role without a factor. Keep both validated factors in the same session; a passkey assertion must not erase the password factor or create privilege for a different principal. Sensitive operations require both factors within five minutes. A test must prove password-only/passkey-only sessions are denied, as are mismatched principals and stale factors.

Before enabling a privileged role, enroll two separately recoverable authenticators, at least one usable independently of the primary device. Role activation/enrollment is a pending ceremony; authenticated recovery does not itself grant a role. A named initial operator is bootstrapped by an auditable, local administrative command in P13/P21, with no default password or public first-admin endpoint. One operator may hold all editorial roles; it does not remove MFA or review evidence.

If one key is lost, use the second plus password, revoke the lost credential and enroll a replacement; revoke existing sessions. If all keys are lost, email reset restores learner access only. Privileged reactivation requires the documented offline operator recovery ceremony: authorized infrastructure-console access with its own MFA, verification against the registered operator record, revocation of old factors/sessions, temporary removal of privileged roles, new authenticated enrollment and an audit event. No support-agent identity guessing or public MFA-bypass endpoint. The sole operator's recovery record and safe custody are U04/P21 obligations; without them privileged production operations cannot launch. This is an operations dependency, not a choice of a second auth system.

## Implementation gates

P07 proves the chosen framework integration; P13 completes all identity journeys; P19 tests enumeration, throttling, CSRF, fixed-origin redirects, ownership, factor recency, session persistence/revocation and recovery. P18 tests the supported browser/authenticator and accessibility matrix. WebAuthn secure-context behavior uses trusted local HTTPS in development. No mail is sent to real recipients or identity provider registered in P03.
