# ADR-006 — Container topology, operations and dated cost model

Accepted as the **reference design**, 23 September 2026. No account, service, purchase, deployment or actual region preference has been selected on the user's behalf. U01/U02/U05/U06 remain launch inputs. [Architecture](../ARCHITECTURE.md).

## Workable local topology

P07 will provide Docker Compose PostgreSQL 18 and a local mail sink, with Java/Next run on the host for development or in containers for full-stack checks. Caddy is the only browser entry at `https://localhost:8443`, using a locally trusted development certificate. It routes `/api/**` to Spring on 8080 and everything else to Next on 3000; infrastructure ports bind loopback only. Public origin includes the port; WebAuthn RP ID is `localhost` without a port. Test certificates and local trust instructions are explicit P07 work, not a request to weaken Secure cookies. CI uses the same single-origin container topology. Local mail is captured, never forwarded externally.

## Reference production topology

Use a **Render Pro workspace**, isolated production environment, one region, with Docker services: Caddy public web service, Next private service, Spring private service and managed PostgreSQL 18. A scheduled backup job connects privately to PostgreSQL and writes client-side-encrypted dumps to a private S3-compatible bucket in DigitalOcean Spaces. SMTP delivery is an adapter configured later; the cost example below is not a provider commitment. Singapore is a latency/cost planning scenario, not an approved data-residency decision; assess users, lawful processing and backup location before P22.

Render edge terminates public HTTPS and forwards to Caddy's platform HTTP port. Caddy restricts Host to the configured public domain, sets security/body/time limits, removes spoofed forwarding/internal-auth headers and routes a fixed path table. `/api` and `/api/**` go to Spring, preserving path; Next owns HTML/assets only. Never expose Spring/Next service ports or management ports publicly. Same-workspace, same-region [private networking](https://render.com/docs/private-network) carries internal HTTP; this design trusts the isolated provider network and privileged workspace operators. It does **not** claim application-level encryption on those internal HTTP hops. DB connections and all external mail/storage links use TLS with certificate verification. A later requirement for end-to-end service encryption adds mTLS by ADR; do not quietly claim it exists.

Normalize proxy behavior at a single ingress: use configured external origin for security decisions and email links, not forwarded host. Do not use client-supplied X-Forwarded-For for account throttling. P21 must establish the trusted platform client-IP chain; until verified, source throttles use the immediate peer conservatively alongside account/global controls. [Caddy's reverse proxy](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy) supports forwarding-header controls and trusted-proxy configuration. Error pages, API responses and HTML are uncached; fingerprinted public assets may use the edge CDN. Caddy admin/config endpoint stays internal. This small proxy is selected instead of business route handlers in Next because it gives both runtimes one explicit ingress and request-limit boundary.

Initial sizing: Caddy 512 MB, Next 2 GB, Spring 2 GB, PostgreSQL 2 GB / 20 GB storage. JVM heap starts at about half the container limit, leaving metaspace/native/thread headroom; Node heap limit also leaves native overhead. These are trial resource ceilings, not a claim of demonstrated throughput. Run one instance of each; startup readiness prevents routing to an unmigrated/broken process. Graceful shutdown drains requests. No persistent application disk or production learner data in containers.

## Recovery and scale

Render Pro [PITR is seven days](https://render.com/docs/postgresql-backups), shorter than the product's backup-retention ceiling. Use daily encrypted logical dumps retained **at most 35 days**, including content/version/audit and learner state, plus encrypted asset manifests. Track backup completion time/restore point and checksum in an independent backup manifest. Alert before the newest recoverable point reaches 24 hours; retry early on failure. The required RPO is ≤24h of recoverable data, not “a cron was scheduled daily.” Use PostgreSQL 18 client tools and tested restore scripts; keep decrypting keys separate from bucket credentials and runtime containers.

Export a minimal deletion/suspension ledger independently of the backup being restored, retaining deletion IDs for 90 days. Account hiding/session revocation happens immediately; completion receipts require durable ledger recording. If the external ledger write fails, retain/retry the pending operation and block an unsafe restore. Before reopening restored data, reapply deletions, expire all restored sessions/tokens, preserve safety withdrawals and reconcile latest publication/account revocations. A backup from before a deletion is never served unfiltered. Cleanup removes old dumps, versions, logs and expired export files including noncurrent object versions.

The independent recovery journal also records role revocations, safety withdrawal IDs and the last acknowledged publication manifest/checksum. These are control records, not note/answer text. A queued journal write may lag the live DB action, but cannot be silently treated as durable: the operations view flags it and a restore with a missing/gapped journal stays quarantined. Reconcile the journal and publication exports before enabling privileged accounts or public lessons after disaster recovery; if reconciliation is uncertain, keep the affected capability disabled for operator review. Content withdrawal provenance is retained with the editorial history, separately from the 90-day personal deletion-ID policy.

P21 must demonstrate a full isolated restore within **four hours from declared recovery start**, record detection delay separately, and verify RPO, ownership, recent deletion and no answer/draft leakage. Require alert coverage to be named under U01; no staffed response is invented. Public reading and authenticated save have separate 99.5% monthly SLOs, one-minute probes, and planned maintenance counts. A four-hour disaster can exceed the 216-minute budget in a 30-day month; neither number excuses that breach. The single-instance baseline has no HA guarantee or contractual SLA.

Scale only on measurement: tune queries/pools first; resize constrained services; add a second Spring/Next/ingress replica and managed DB HA if the SLO warrants it. JDBC sessions, versioned reads and database job leases already work without sticky sessions. Pool totals remain below database limits; rolling deployments use schema compatibility. No shared HTML cache means no cross-replica ISR state to coordinate. Add Redis/search service/queue only through an observed bottleneck and a migration ADR; split domain services only with independent ownership or scaling evidence. Re-price HA and replicas before approval; current envelope does not include them.
