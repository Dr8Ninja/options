# ADR-002 — Next.js rendering, with Spring as the application authority

Accepted for design, 23 September 2026. [Architecture](../ARCHITECTURE.md).

## Comparison and decision

| Option | Public content / SEO | Private experience and accessibility | Complexity and deployment | Disposition |
|---|---|---|---|---|
| Next.js App Router + React + TypeScript | Server-rendered substantive HTML, metadata and route boundaries; static generation also available | Shared accessible forms/components for lessons, saved learning and editing; framework does not confer WCAG compliance | Node runtime and careful cache/cookie boundaries; familiar typed React model without assuming user expertise | **Selected**, using dynamic SSR and small client components |
| React Router framework mode | Official [SSR and prerendering](https://reactrouter.com/start/framework/rendering) support, so a credible alternative | Equally capable private React UI | Comparable Node deployment; loaders/actions would still need strict Spring ownership | Rejected for R1 because Next's integrated route metadata, rendering and asset conventions reduce separate assembly; no claim Router cannot meet the contract |
| Astro + React islands | Strong content-first static delivery, [on-demand SSR available](https://docs.astro.build/en/guides/on-demand-rendering/) | Forms are possible; persistent learner/editor flows need coordinated islands or a second app pattern | Attractive for a primarily read-only publication; adds two UI composition models here | Rejected because R1 already includes substantial private assessment/editorial interaction |
| Vite React SPA | Client application works; a plain SPA does not deliver the required substantive HTML without another SSR/prerender layer | Good interactive UI, but initial reading depends on JS | Simplest static hosting becomes more complex after adding required SEO rendering | Rejected for this release contract |
| Spring MVC + Thymeleaf, progressive enhancement | Excellent server HTML, one runtime, lowest operations footprint | Accessible forms possible; richer note conflicts, quiz feedback and editor preview need deliberate JS integration | Valid smaller alternative, less unified typed component model across interactive journeys | Rejected in favor of one React presentation model across public/private/editor screens; operations cost is explicit in ADR-006 |

This is a project fit decision, not a framework benchmark. P20 must measure the selected implementation against P02 budgets.

## Runtime and rendering contract

Next runs as a **Node server with standalone output**, built in CI with public assets and `.next/static` included in the image. It has no database driver/credentials, scoring, role decisions, email sender or content-writing service. No Next Server Actions for business mutations and no parallel API backend. Browser mutations go directly through the same-origin proxy to Spring. Server components may call Spring for read DTOs; they never bypass authorization. Next's Proxy hook is used only for rendering headers/nonces and redirects for presentation, never as the security boundary.

R1 uses dynamic SSR for all content HTML, including anonymous pages, and explicit `no-store` on API fetches and HTML responses. It does **not** use ISR, Cache Components, a shared HTML cache or CDN caching of API/HTML. This avoids coupling publication correctness to multiple invalidation systems at this small catalog size. The [self-hosting guide](https://nextjs.org/docs/app/guides/self-hosting) distinguishes server caches, immutable assets and multi-instance concerns. Only fingerprinted public JS/CSS/fonts/owned images use long-lived immutable caching. This costs rendering CPU; two-GB Node sizing and P20 load tests are required.

Use a per-response CSP nonce with dynamic rendering, following [Next's CSP guidance](https://nextjs.org/docs/app/guides/content-security-policy). Do not combine per-request nonces with cached HTML or experimental static SRI. Public lessons use server-rendered restricted Markdown, math and tables, with client islands for bookmarks/practice; load editor and quiz code only on relevant routes. No hosted calculator, live market chart, third-party video embed or remote font enters the R1 critical bundle. Original videos remain external links with metadata.

Anonymous public fetches deliberately omit incoming cookies, authorization and private headers. A logged-in user's public lesson is still public content; personal controls load separate owner-scoped DTOs. Private SSR reads forward only the session cookie to a fixed internal Spring origin and use `no-store`; no cookie is forwarded to a resource URL. Spring's `/me` result may help render a login redirect but a second API call must independently authorize. All private/error/preview routes are noindex and uncached. Auth mutations occur in the browser so every `Set-Cookie` reaches it; do not attempt login in a server component.

Soft navigation must not create a stale-content loophole: disable content-link prefetch in R1; refresh the active content revision/status at navigation, on foreground focus and every 30 seconds while visible. On withdrawal replace the current view with a correction notice; on revision change offer the new version without discarding unsaved private input. Old content already read or copied cannot be recalled. New server requests must use the current release/withdrawal state, with a 60-second end-to-end detection gate. Browser back/forward cache restoration revalidates private session and clears stale private views before allowing interaction. Sign-out/account switch clears in-memory client state and uses a full navigation; no service worker or private localStorage/IndexedDB.

Static-only hosting cannot satisfy this design: [Next static exports](https://nextjs.org/docs/app/guides/static-exports) exclude request-time cookies, rewrites, headers, ISR and dynamic server behavior. Hosting an `out/` directory would be a changed architecture, not a cheaper equivalent deployment. CDN delivery of immutable assets remains compatible with the chosen runtime.

## Quality consequences

Use semantic HTML, real labels, focus/error summaries, accessible MathML plus textual reasoning and numeric tables. Theme tokens support system/light/dark without blocking reading. Follow REQ-14/15 for keyboard, zoom, screen reader and browser matrices; a framework accessibility claim is not test evidence. Public text and navigation remain usable without JavaScript; account saving and scored assessment require JS with an explicit explanatory fallback. Unknown/loading/offline/error states follow REQ-13. Estimated durations and planned content stay honest; metadata-only topics have no Start button.
