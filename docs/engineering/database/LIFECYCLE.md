# P04 lifecycle, import and migration contract

Design dated 23 September 2026; [schema](SCHEMA.md), [canonical mapping](CANONICAL_MAPPING.md), [P03 authority decision](../adr/005-editorial-authority.md). PostgreSQL behavior is a design dependency; transaction/recovery tests remain P08–P21.

## Authority and state transitions

Canonical files are the bootstrap and reviewed interchange. After bootstrap, database revisions are authoritative; Git edits are proposals with explicit base revisions. Neither an import nor a file export can overwrite admin edits silently. No periodic folder synchronization is authorized.

| Aggregate | Allowed lifecycle | Guard and result |
|---|---|---|
| Revision body | assemble → sealed | One transaction inserts common/detail/sections/links and verifies hash/completeness; no externally visible partially built revision; any later edit creates another revision |
| Draft head | DRAFT → IN_REVIEW → APPROVED; review rejection → DRAFT | Expected lock version, exact revision/hash; changing a reviewed body creates a new DRAFT and needs new reviews |
| Publication | BUILDING → SEALED → selected by active pointer | Candidate closure, review, rights, readiness and graph checks; no direct DRAFT-to-public shortcut |
| Stable object | active → retired; reviewed restoration allowed | Retire via editorial transaction plus new manifest; preserve routes, mappings and learner references; don't hide historical evidence |
| Withdrawal | active → reviewed reinstatement | Safety overlay is independent of publication; rollback cannot reinstate it; public message is safe text |
| Import run | VALIDATING → REJECTED / CONFLICTED / STAGED → APPLIED | Report immutable after validation. APPLIED means accepted draft proposals, never publication. A conflicted run requires new reviewed package/revalidation; it cannot partially publish |
| Attempt | STARTED → SUBMITTED or ABANDONED | Submission terminal and idempotent; abandoned exposure remains; completed score cannot be edited |
| Dossier | DRAFT → SELF_REVIEWED | Numeric/self-rubric checks and explicit critical-error acknowledgement; another review is a new submission, never professional certification |
| Account | UNVERIFIED → ACTIVE ↔ SUSPENDED → DELETING → erased | Generation/session revocation on security changes; DELETING cannot be reopened by a stale request |

Readiness remains separate from all these workflows. A metadata map entry can be approved with a scope outline, while LESSON requires authored/reviewed content and complete teaching/assessment evidence. A blueprint is not an executable quiz. R1 lessons, six gates/two forms each and dossier must be authored in P17; this snapshot creates none.

## Import protocol

1. **Receive and identify.** Authenticated privileged operator supplies a bounded package with schema version, unique package ID, source manifest, per-file SHA-256 and base publication/revision IDs. Allowlisted relative files only; reject traversal, symbolic-link escape, executable Markdown, external fetch directives, unknown schema fields and oversized inputs. Record the original artifact privately before parsing. Maximum package 100 MiB, 1 MiB per archived record, 2 MiB report; oversized lawful source artifacts require a separately reviewed source-only upload, never truncated records.
2. **Validate without mutation.** Check inventory/source hashes, all 22 collections and manifest, global IDs/types, every relation target, original mapping coverage, date/metadata precision, ordered arrays, cardinality, prerequisite graphs, typed details and source field dispositions. Bootstrap has null bases; after bootstrap every existing object needs a known base revision. Preview adds/unchanged/edits/retire requests/conflicts, by external ID and field, with no learner information. Missing records are reported as absent, **not deleted or retired**. All 6,402 source mappings and 28 archival structures remain preserved.
3. **Compare three versions.** Base B, current draft/head C, proposed P. If P=B, keep C. If C=B, P may be staged. If C=P, no-op. Otherwise conflict: show B/C/P to authorized editors. R1 does not auto-merge even apparently disjoint edits. An explicit reviewed merge creates a new proposal based on C. Identity kind changes, reuse of an old slug, lost protected fields and source-hash mismatch reject, not merge.
4. **Stage atomically.** Acquire the import-hash and graph locks; recheck bases under row locks. All reference/graph failures roll back the entire content transaction. All-valid packages produce immutable proposed revisions and `import_proposal` records; no current head changes until apply. A package with conflicts may preserve safe preview proposals, but no head is updated; the report must clearly show this state. Staged orphan candidates are private, audited and not reachable by public manifests.
5. **Apply proposals, not publication.** Revalidate current heads, rights and all accepted graph changes. One transaction switches draft heads, appends audit, marks APPLIED and queues export. A race becomes a conflict and changes no heads. Exact same manifest replay returns the applied batch and creates no revisions or learner changes. Concurrent same-hash requests serialize; explicit revalidation is the next numbered run. One APPLIED row per manifest prevents duplicate application. Different bytes under a reused package ID are rejected until a new ID is supplied.
6. **Review and publish separately.** Workflow below controls visibility. Imports use an import/system actor with source verification dates explicitly distinguished from new review dates. Imported verification claims do not create reviewer approvals or current rule certifications.
7. **Export and round-trip.** After commit, a leased job writes a versioned editorial package with exact selected IDs/revisions, typed associations, order, raw date precision, null/unknown reasons, source anchors and provenance. Repository write failure leaves database truth intact and a retryable job. Separate protected editorial/source archive and distributable public allowlist exports; no learner records, answer keys or restricted source prose in public exports. Export job verifies object count, relationship tuples and hashes, then atomically renames the completed artifact. Never commit secrets or account data.

The immutable JSON import report contains only schema-versioned codes, source pointers, counts, IDs, hashes, conflict fields and sanitized diagnostics. It is not queried as domain data. The original JSON `source_record.original_payload` and original artifact bytes are the other archive exceptions. Operational catalog relationships always use joins. Byte-exact original reproduction uses the artifact; semantic canonical reproduction uses relational fields, not a lossy reconstructed summary. JSON object key order is not meaningful; array order, numbers, nulls, source types and strings are. P09 must prove a normalized round-trip and compare every source record, not just row counts.

For old stage records, export reconstructs `original` from the archived JSON pointer; stage names are not current phase entities. For supplemental Markdown, source hash/line anchor and exact prose survive alongside application-readable archival sections. Supplement not intended for public use stays restricted. For a merged resource, retain both external identities and redirect/disposition links; new assignments can use the chosen survivor, existing versions still point to their original resource. Topic splits do not silently copy progress/mastery to two new lessons. Notes remain on the original identity with a replacement notice; users may explicitly copy their own text later, if an API is deliberately added.

## Publication, correction and rules

Build a candidate manifest from the active one plus approved selections. Under the graph lock and publication pointer lock, verify expected generation, whole-manifest closure, typed cardinalities, hierarchy uniqueness, ordered membership, hard/recommended DAGs and same-kind successor chains. Resolve every common stable link through this one manifest; exact assessment/rubric/rule references must match its protected or public entries. Validate each visibility:

- MAP: approved safe metadata, honest planned/readiness labels and rights to show it; no answer text or restricted archive body.
- LESSON: exact technical, pedagogy, accessibility and rights approvals; associated practice/feedback and assessment where required; no unresolved core claim or stale current operational dependency.
- PROTECTED: quiz/form/question keys, reference behaviors and protected editorial evidence with required assessment/rights review. Presence in a manifest is not permission for the public serializer to disclose it.
- ARCHIVE: source-preservation entries accessible only to authorized editorial export/preview; never indexable.

Select allowed public fields into `public_search_document` within the activation transaction at this small scale, then seal manifest, append audit/job/journal and advance singleton generation. Search and catalog see the same publication immediately; asynchronous external export is not on the request path. No shared SSR/HTML/API cache is enabled in P03. If a rebuild exceeds the transaction budget, build candidate search rows beforehand and validate their manifest/hash at activation; never activate with missing search. P20 proves ≤60-second publication visibility and actual latency.

Critical correction first withdraws affected revision/object, increments publication generation, records issue impact and queues affected enrollment/evidence rechecks. Public reads check withdrawal at query time; multi-query responses use one snapshot then recheck live generation/withdrawal before responding. If it changed, retry once against current state or return a safe retry response. Responses already delivered cannot be recalled; clients refresh on resume. Private old scores retain historical labels. Administrative rollback selects previously approved revisions in a new manifest with a new audit event, revalidates current rights/rule exclusions and preserves withdrawals. Reinstatement requires a new explicit review; a cached approval of the withdrawn body is insufficient.

Rule eligibility is computed using request instant converted to the recorded market zone, known effective interval, current scoped verification, active certification, no active withdrawal/supersession and `request_time < review_due_at`. Historical use can remain eligible only for its labeled date/scope. Imported `publication_eligible` maps to historical scope; all 27 `current_operational_publication_eligible=false` values remain false. An unknown effective end does not become infinity: a certification can grant a **bounded verified-as-of window**, ending no later than the next scheduled review, without pretending the underlying rule expires then. The raw observation retains its unknown actual end. India review interval seven days; other current rules thirty days; authoritative contrary evidence overrides any remaining timer immediately. Resource section reviews have a 180-day due target, separate monthly link checks. Failed transport creates a link issue, not proof the educational claim is false.

The nonoverlap constraint applies only to active certifications for the same precisely defined subject. Endpoints are finite and exclusive; an approved replacement revokes the old certification and installs a newly bounded window in one transaction. Conflicting raw observations remain archived. The design uses PostgreSQL [range bounds](https://www.postgresql.org/docs/18/rangetypes.html) and [btree_gist scalar/range exclusion support](https://www.postgresql.org/docs/18/btree-gist.html); P08 must test actual overlap enforcement and extension permissions. Publishing a current-rule lesson also requires explicit `rule_dependency` rows so due/withdrawal impact can be located.

## Transactions and concurrent requests

Default isolation is READ COMMITTED for short writes using explicit locks and checked updates; public multi-query aggregates use READ ONLY REPEATABLE READ plus final live withdrawal check. Atomic statements with unique/FK constraints remain the primary defense. Isolation alone does not prove a graph invariant; see PostgreSQL [isolation](https://www.postgresql.org/docs/18/transaction-iso.html) and [locking](https://www.postgresql.org/docs/18/explicit-locking.html).

Global lock order where needed: import-hash/graph advisory lock → active publication row → account rows in ID order → catalog object/draft rows in ID order → enrollment → attempt/project → queue row. A transaction takes only needed locks, always in this order; workers release job-claim transactions before domain operations. Content-only work need not lock unrelated accounts. Role revocation, deletion and every owned write lock/check the subject account first, preventing a delayed note/attempt write from succeeding after erasure has begun. At R1's 50 concurrent sessions the short per-account critical section is a deliberate simplicity tradeoff, not a whole-system lock.

| Operation | Boundary and conflict response |
|---|---|
| Draft edit / note / profile / reopen | `UPDATE ... WHERE id=? AND lock_version=?` plus ownership; zero rows distinguishes missing/forbidden without disclosure or a genuine version conflict after owned lookup. Return current version and safe own text; retain unsaved client text only in memory. No last-writer-wins |
| Reorder contents | New parent revision with complete ordered join set, unique positive ordinal; no in-place half reorder. Ordinals may have gaps but exporter sorts deterministically; duplicates fail |
| Bookmark | Owner/object unique key makes repeated save idempotent; delete only owned row. No version conflict needed for identical set membership |
| Enrollment | Lock account then current enrollment; ensure fully publishable course and snapshot all 43 R1 requirements in one transaction. Unique active enrollment stops duplicate starts |
| Start/resume gate | Lock account/enrollment; verify earlier required gates/remediation, allocate genuinely unexposed form and atomically record STARTED plus exposure. Network retry with same request key returns same attempt; existing started attempt resumes instead of consuming another form |
| Submit gate | Lock account/enrollment/attempt; reject different body for used request key; validate membership/types/units, compute against pinned keys, insert answers/result/evidence atomically. Return existing result for identical retry. Never use client scores |
| Freshness/retries | Exposure happens on first prompt delivery, even abandoned. The first attempt may be fresh despite creating its own exposure row; freshness means no prior exposure before this attempt. Failed gate requires remediation then the other reviewed form; both exhausted creates assessment_request. Cosmetic re-versioning cannot reset exposure |
| Dossier self-review | Lock owner/work; validate all required fields, weighted rubric and critical acknowledgement; seal responses together. Do not convert self-review to demonstrated mastery |
| Job execution | Short `FOR UPDATE SKIP LOCKED` claim, lease token, commit, work outside lock, fenced completion. Durable dedupe prevents duplicate domain effects; retryable SMTP may duplicate email delivery, never consume a token or send an order twice |
| Rule certification | Lock subject plus graph/publication where eligibility changes; verify no overlap, append verification and bounded certification, increment generation, queue impact. Live due checks remain safe if queue is delayed |

Request-body digest canonicalization excludes server timestamps and includes every submitted answer; SHA-256 is an idempotency checksum, not a password hash. On serialization/deadlock errors retry the entire transaction at most three times with bounded jitter and the same idempotency key; do not retry validation/authorization failures. Never perform SMTP, network verification, renderer downloads or object-storage writes while holding database locks. Statement timeout 5s, lock timeout 1s for interactive transactions as starting configuration; bulk staged imports use a separately bounded 30s transaction after offline parsing. P20 must measure and adjust without changing semantics.

## Learner versioning and privacy

Completion is self-reported per topic revision; mastery requires attributed evidence. Progress numerator joins exact frozen requirement revisions or reviewed equivalences; denominator counts required topic requirements only, deduplicated by stable object. Gates and dossier are separate measures. Optional work never enlarges the required denominator. Recommended preparation may explain a suggestion but cannot make a gate fail. A retired lesson leaves a visible blocked requirement; a finished course keeps its historical version label and any critical recheck flag.

A migration to a new course is explicit: show changed requirements/equivalences, preserve old enrollment, create the new snapshot and supersede the old active enrollment in one transaction. Notes/bookmarks attach stable objects and survive; old attempts stay pinned. Historical attempts may satisfy the new snapshot only by exact version or approved evidence equivalence and no unresolved recheck. Recompute derived summaries with an algorithm version; do not rewrite submitted answers/scores. After both fresh forms fail, repeated PRACTICE attempts may show feedback but cannot satisfy a gate; new evidence awaits a genuinely new reviewed form. No separate summary cache table is needed at the initial scale.

| Data class | Retention / export / erasure |
|---|---|
| Account/profile/roles/credentials | Owner export excludes hashes, secrets and credential key material. Unverified accounts expire after7 days; active accounts retained until deletion or24 months inactivity plus30-day notice. Deletion immediately disables/revokes, purges live owned records within7 days. Role removal increments generation and clears sessions |
| Notes/bookmarks/progress/attempts/exposures/remediation/practice/dossier | Account-owned; export own plain text, structured responses, pinned IDs/version/score/times with labels; no unpublished keys. Explicit note/dossier-writing delete removes live text immediately, including owned submission copies, and removes derived self-review evidence. Account erasure cascades all owned learning data. Neither import nor content retirement deletes these rows |
| Sessions/tokens/challenges/throttle | Ephemeral, outside logical recovery export. Expired/revoked tokens removed within24h; framework TTL cleanup for sessions/challenges, bounded throttle windows. Revoke tokens and sessions on password/security generation changes. Recovery never restores usable sessions |
| Issue reports / requests | Closed volunteered issue text purged after90d; account deletion removes report ownership/text. Exhausted-bank queues contain no answer/private-note text. Privacy receipts minimal,90d; export ready target24h, private download expires24h after ready; object deletion verified |
| Content/reviews/provenance | Retain for source/audit/version integrity; pseudonymous actor only after account erasure. No email/profile or learner text in revision hashes/audit. Source artifacts restricted by rights, not learner-private storage |
| Operational telemetry | Sanitized security events90d, request logs30d, aggregate necessary product metrics90d. No persistent raw search queries, note bodies, answer bodies or session secrets in logs/import reports. Metrics are operational aggregates, no new analytics event store |
| Backups and recovery journal | Encrypted backups expire within35d under P03. Minimal erasure/revocation/withdrawal journal independently retained90d and replayed before recovered service is accessible; no private content in journal. Individual rows cannot be reliably removed from immutable backup files; expiry plus replay prevents resurrection |

MAIL jobs carry a typed delivery purpose, account generation, bounded expiry and a pending new email only for CHANGE_EMAIL. The worker rechecks active intent, account state/generation and expiry, generates a token in memory and persists only its digest before sending. A newer same-purpose intent cancels prior pending intents; uncertain delivery retries replace/invalidate the previous token, consistent with P03. No raw token is stored in the job; terminal intent/email data is purged within24h.

Individual note/dossier-writing deletion also appends minimal typed NOTE_ERASE/PROJECT_WRITING_ERASE journal entries with owner UUID and each erased record public UUID. Replay deletes those exact records and their derived self-review evidence; it never logs the text or revives a submission from an older backup. These no-FK tombstones are a deliberate, narrowly typed recovery exception.

An account erasure transaction nulls editorial actor account links, deletes account-owned rows, preserves pseudonymous content events and appends the minimal public UUID deletion receipt. Recent-auth/CSRF and verified ownership are required for export/delete; admins cannot use the owner endpoint to read another learner's notes. Background privacy worker receives only an authorized request ID and purpose. No application endpoint exposes broad database administrator privileges. Journal events are independently acknowledged before a destructive action is reported fully complete; failure leaves a visible retrying privacy request, keeps the account disabled and alerts the operator. Restore blocks ingress until it reconciles journal sequence/watermark, replays deletions/suspensions/role revocations/withdrawals, discards all sessions/tokens and verifies a clean public manifest. Expired artifacts and restored stale export objects must be purged before serving downloads.

## Incremental P08 migration plan

These are ordered migration **design groups**, not created SQL files. P08 assigns exact Flyway numbers and tests forward migrations against PostgreSQL18, never Hibernate auto-DDL.

| Group | Introduced representation | Proof before next group |
|---|---|---|
| DB01 | Required extension btree_gist; catalog_object skeleton; account/role/actor/security/session tables | Actual framework session DDL compatibility; privilege separation; empty DB startup; no default admin password |
| DB02 | Catalog revisions/routes/tags/sections/typed links/prerequisites, fixed kind/endpoint checks | Duplicate ID/route rejection, wrong-kind FK rejection, immutable aggregate and concurrent cycle tests |
| DB03 | Typed content/resource/assignment/rubric/blueprint/path details | Completeness trigger, contextual resource reuse, protected fields and unknown metadata round-trip |
| DB04 | Source artifacts/anchors/mappings/archives/claims/verification and authoring queue | Full canonical field/source preservation; referenced source IDs exist; restricted archive export isolation |
| DB05 | Rule observations/notices/supersession/certifications/dependencies | Date bounds/overlap/supersession conflicts, unknown-end bounded verification, stale eligibility under clock advancement |
| DB06 | Publication/reviews/withdrawals/import/proposals/search/audit/jobs/recovery | Atomic activation, stale base conflict, safe rollback, lease retry; source_mapping/import circular creation FKs added after both tables exist |
| DB07 | Executable quizzes/questions/forms/course gates/projects, enrollment/owned learning/evidence | Exact question membership, owner mismatch rejection, immutable results, R1 denominator and exposure retry tests |
| DB08 | Privacy/issue/request tables and remaining cross-group FKs; search/ownership indexes; runtime grants | FK catalog audit, erasure without content loss, import role barred from learner writes, export/deletion/recovery fixtures |

Forward references (account interest→catalog kind, import audit/batch, job→privacy request) are added in the appropriate later group before granting runtime access. First create table/key targets, then add cyclic-context FKs; cyclic domain dependency is not required. Separate migration role owns DDL; runtime role cannot migrate, disable triggers or mutate sealed revisions. Importer service receives no learner write repository and its dedicated DB role lacks owned-data DML. Public reads use explicit projections, not entity serialization; privileged DB credentials never reach Next.

Use additive expand/backfill/validate/contract for populated deployments; backfill in bounded batches, inspect constraints before making columns NOT NULL. At this scale initial indexes can be transactional. Future `CREATE INDEX CONCURRENTLY` needs a separately configured nontransactional migration and invalid-index recovery procedure. Never edit an applied Flyway file; checksum mismatch stops startup and is investigated. Roll back an application only to a schema-compatible artifact, use forward corrective migrations for schema issues, and restore backups only under the deletion-aware recovery procedure. P08 must exercise both clean creation and upgrade from each seeded prior migration group, with negative cases on real PostgreSQL rather than an in-memory substitute.
