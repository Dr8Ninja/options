# Account identity operations — P13

P13 uses Spring Security DAO password authentication, Argon2id and PostgreSQL Spring Session; Spring's WebAuthn4J relying-party operations verify credentials. This is the ADR-004 decision. No social-login provider or separate identity service is introduced.

## Deployment boundary

Serve frontend and `/api/v1` behind one HTTPS public origin. Set `APP_ENVIRONMENT=PRODUCTION`, exact `PUBLIC_ORIGIN=https://your-owned-host`, and the frontend's private `API_INTERNAL_ORIGIN` to the backend origin. Do not expose the backend listener or management port to the public network. CORS is disabled. Do not forward arbitrary browser Cookie/Authorization headers to other origins. Origin checking uses the configured origin rather than untrusted forwarded host headers. The RP ID is the public origin's host; changing it requires credential re-enrollment.

The cookie is `__Host-OTRSESSION; Secure; HttpOnly; SameSite=Lax; Path=/` with no Domain. HTTP localhost is not the authentication deployment. Use the provided trusted local HTTPS proxy. Spring rotates the session ID and CSRF state at password authentication, reauthentication and security-key verification. Learners have 24-hour idle/7-day absolute expiry; unverified sessions have 15-minute idle expiry and cannot access owner data; privileged sessions have 15-minute idle/8-hour absolute expiry. Sensitive changes need password authentication within five minutes and, for privileged users, WebAuthn within five minutes. Passive session-status polling does not refresh the authoritative idle deadline; the account page warns within five minutes of expiry. Revocation generations are checked on every request and database triggers delete outstanding sessions when credentials/status/roles change.

Password policy normalizes NFC, accepts 15–128 Unicode code points, rejects the bundled common-password list and uses Argon2id (19 MiB, two iterations, one lane). Two concurrent hash operations per process bound memory; exhausted capacity returns 503. Identity bodies are capped at 64 KiB. PostgreSQL rate buckets survive restarts: ten consecutive bad passwords with no 15-minute gap trigger a 15-minute address lock; source 100/15 minutes and global 300/minute login budgets; mail requests five/address/hour, 20/source/hour and 200/global/minute. Successful login clears its address failure counter. Unknown addresses consume the same budgets. Source is the actual TCP peer; forwarded IP headers are not trusted. In the supplied single-proxy deployment this conservatively aggregates clients at the proxy. Before scaling, add a trusted edge per-client limiter; do not simply trust arbitrary X-Forwarded-For. Global/application limits remain required.

## Mail modes and templates

Default `IDENTITY_MAIL_MODE=DISABLED` sends nothing. Requests still acknowledge eligibility without claiming delivery. The local compose stack explicitly sets `LOCAL`, host `mailpit`, port `1025`; its mail UI is loopback-only at the port in compose. Standalone development can use `LOCAL`, `127.0.0.1`, `1025`. LOCAL rejects remote hosts and production environment. Tests use a disposable pinned Mailpit container; all recipients are `.invalid` addresses.

For an authorized external provider configure `IDENTITY_MAIL_MODE=SMTP`, `IDENTITY_MAIL_HOST`, `IDENTITY_MAIL_PORT` (default 587), `IDENTITY_MAIL_FROM`, `IDENTITY_MAIL_USERNAME` and `IDENTITY_MAIL_PASSWORD` through the deployment secret store. SMTP requires authentication, STARTTLS and hostname verification with three-second connect/read/write timeouts. Configure sender/domain authentication and provider limits with the operator. These values are never `NEXT_PUBLIC_*`. No provider is selected and no external delivery has been exercised or authorized in P13.

Plain-text templates in `IdentityMail` include the purpose-specific confirmation route, expiry, single-use warning and ignore-if-unrequested guidance. Only short-lived mail intents are persisted; tokens are minted just before SMTP and are never stored in a durable payload. A successful SMTP acceptance commits the digest, not a claim of inbox delivery. A crash after SMTP but before commit can leave an unusable message: request the latest message. Failed intents/notices have five-minute retry delays and at most ten attempts. Intents expire after 30 minutes; notices after 24 hours. Hourly cleanup removes expired intents, notices, challenges and old token metadata. A bounded database capability also deletes up to 100 abandoned unverified registrations older than seven days, revokes their sessions through existing cascades and records an opaque erasure journal entry. It cannot erase active accounts; the runtime still has no general account-delete privilege. Never enable SMTP message/debug logging.

## Initial administrator and privileged recovery

1. Register normally, verify using the configured mail service and sign in. Enrollment always grants only learner access.
2. Enroll two independently recoverable, user-verifying authenticators on the account page. Two registrations alone cannot establish independent custody; the accountable operator checks this outside the application.
3. Use `scripts/identity-operator.py invite --account ACCOUNT_UUID --role ADMIN --operator-record CHANGE_REFERENCE` on a controlled operator host with `IDENTITY_OPERATOR_DSN` supplied through a secret environment. Use an operator database credential; the runtime role cannot insert invitations or grant account roles. No password or DSN belongs in command arguments or source control.
4. Within 24 hours, after verifying custody and identity, run the same command with `activate` and `--independent-keys-confirmed`. Activation requires a matching invitation/reference, an active verified account and two unrevoked user-verifying keys. Roles/session revocations and a security event are persisted. Sign in again and verify a key.
5. For lost/compromised privileged credentials use `recover` with the account/reference, after offline identity verification. It removes privileges/invitations, revokes authenticators and sessions. Repeat the invitation/enrollment ceremony. Email-only recovery never restores privileged access.

Use `--role EDITOR` or `REVIEWER_PUBLISHER` only for a justified assignment. Operator events/reference records are accountability evidence, not fabricated independent review. Do not make these commands a public HTTP endpoint. Password reset removes privileged roles; loss of all factors requires operator involvement. Removing a privileged key requires enrolling its replacement first so two remain.

## Validation and known limits

Run `scripts/test-identity.py` with the Python environment containing the existing pinned PostgreSQL operator dependency, Java 25, Node 26, Docker and the built frontend. It uses disposable databases/mailboxes and an ephemeral test-only operator DSN, removed at shutdown. No accounts are seeded into the persistent local content store. API responses, role enforcement, local delivery, browser deep links and isolation are validated at this boundary; production DNS/TLS/provider deliverability and independent key custody remain deployment/operator checks. Existing image release blockers remain tracked separately.
